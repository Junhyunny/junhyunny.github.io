# 블로그 글 첨삭

대상은 사용자가 지정한 글(`PATH`)입니다. 지정하지 않았으면 IDE에 열린 `src/content/posts/`(또는 `logs/`) 파일을 쓰고, 그것도 없으면 어떤 글인지 물어봅니다. 파일이 없으면 `오류: 파일을 찾을 수 없습니다: <PATH>`를 알리고 멈춥니다. 글 하나를 처음부터 끝까지 읽은 뒤 아래 순서대로 작업합니다.

글 형식은 `README.md`의 "새 글 작성"과 `src/content.config.ts`의 스키마를 따릅니다.

## 공통 원칙

- 글쓴이의 사실, 주장, 경험, 말투를 지킵니다. 글에 없는 사실, 수치, 일화를 지어내지 않습니다. 뜻이 바뀔 수 있으면 고치지 않고 보고합니다.
- 문단과 섹션의 순서는 필요할 때만 바꿉니다.
- 다음은 아래 단계에서 정한 경우가 아니면 고치지 않습니다: 코드 블록과 인라인 코드 안의 내용, URL, 링크 정의의 식별자(`[cors-link]: ...`), HTML 속성과 클래스 이름, CodePen 삽입 코드, 고유명사.
- frontmatter의 `title`, `canonicalPath`, `categories`, `tags`는 고치지 않습니다. `title`의 오타는 보고만 합니다. (예외: 1단계 `PROMPT`, 9단계 새 글)
- 날짜 필드와 파일 이름은 9단계 규칙으로만 바꿉니다.

## 1. PROMPT 지시문 처리

`PROMPT(...)`는 글쓴이가 AI에게 남긴 지시문입니다. 괄호 안 문장을 그대로 싣지 않고, 지시를 수행한 결과로 `PROMPT(...)` 전체를 바꿉니다. 본문과 frontmatter(`title`, `summary`)를 모두 찾습니다. 코드 블록과 인라인 코드 안의 `PROMPT(...)`는 예시이므로 건드리지 않습니다.

- 괄호 안에 괄호가 있으면 짝이 맞는 닫는 괄호까지가 지시문입니다.
- 지시문이 짧거나 문장이 끝나지 않았으면 놓인 자리로 뜻을 판단합니다. 예를 들어 `summary: "PROMPT(글 내용을 보고 )"`는 글 내용을 보고 요약을 쓰라는 뜻입니다.
- 결과는 글의 문맥에 이어지게 쓰고, 이 스킬의 문체 규칙을 따릅니다. `summary`는 글 목록과 검색 결과에 보이는 한두 문장으로 씁니다.
- 수행하려면 글에 없는 사실이 필요하면 지어내지 말고 `PROMPT(...)`를 그대로 둔 뒤 무엇이 필요한지 알려 줍니다.

## 2. 첨삭

- 오타를 고칩니다: `않되` → `안 되`, `됬` → `됐`, `몇일` → `며칠`, `~로서`/`~로써`, `~던`/`~든`, `~데`/`~대`를 문맥에 맞게 구분하고, 중복된 단어와 문장 부호를 지웁니다.
- 띄어쓰기를 한국어 맞춤법에 맞춥니다: `이 것` → `이것`, `그 동안` → `그동안`, `할수있다` → `할 수 있다`, `하는것` → `하는 것`, `못 했다` → `못했다`(불능), `사용시` → `사용 시`. 조사는 앞말에 붙여 쓰고, 숫자와 단위는 붙여 씁니다(`3번`).
- 어색한 표현, 번역투, 끊기거나 비문인 문장을 자연스럽게 고칩니다. 예: `~에 대해서 생각해보면` → `~을 살펴보면`. 조사(`을/를`, `이/가`, `은/는`)를 문맥에 맞추고, 지나치게 긴 문장은 나눕니다.
- 같은 단어나 표현의 반복을 줄이고, 뜻이 겹치는 문장은 하나로 합칩니다. 강조나 리듬을 위해 일부러 반복한 표현은 둡니다.

## 3. -이다 어체로 통일

본문 문장, 목록 항목의 문장, 문장으로 끝나는 `summary`와 소제목을 `-이다` 어체(`-이다`, `-한다`, `-했다`, `-있다`)로 맞춥니다. `-습니다`, `-입니다`, `-해요`, `-이에요`, `-함`이 섞이지 않게 합니다.

- 독자에게 권하는 `-해보자`, `-살펴보자`, `-보겠다`는 이 블로그의 말투이므로 유지합니다.
- 1인칭은 `나`, `내가`로 씁니다. `저`, `제가`는 쓰지 않습니다. 글쓴이가 쓴 `필자`는 그대로 둡니다.
- 의문문은 `-까?`, `-나?`로 씁니다. `-까요?`를 쓰지 않습니다.
- 해요체에서만 쓰는 말끝을 풀어 씁니다. `-거든요`는 `-기 때문이다`, `-죠`와 `-네요`는 `-다`로 바꿉니다.
- 같은 어미가 연달아 나오면 문장을 합치거나 어순을 바꿔 단조롭지 않게 합니다.
- 말끝을 지나치게 딱딱하거나 단정적으로 만들지 않고, 글쓴이의 차분한 말투를 유지합니다.
- 다음은 그대로 둡니다: 명사로 끝나는 제목과 목록 항목(`JDK 7 버전부터 Heap 메모리 영역 사용`), 인용문, 프롬프트 원문, 코드, 로그.

## 4. 소제목

이 블로그는 번호가 붙은 소제목을 씁니다: `## 0. 들어가면서`, `## 1. ...`, `### 1.1. ...`, 마지막 `## CLOSING`, 그 뒤 `#### TEST CODE REPOSITORY`, `#### REFERENCE`.

- 같은 수준의 번호가 이어지는지 확인합니다. `### 3.1.` 없이 `### 3.2.`가 나오면 `### 3.1.`로 고칩니다. 번호 형식(`1.`, `3.1.`)은 글의 기존 형식을 따릅니다.
- 번호를 바꾸면 본문에서 그 소제목을 가리키는 문장(`3.2절에서`)도 함께 고칩니다.
- 한 번호 구간이 길고 주제가 뚜렷이 나뉘면 하위 소제목(`### 2.1.`)을 넣습니다. 두 문단 이상을 묶을 수 있을 때만 넣고, 제목은 그 구간을 요약한 짧은 명사구로 씁니다. 하위 소제목이 하나뿐이 되면 넣지 않습니다.
- 글쓴이가 쓴 제목은 유지합니다. `#`(h1)은 쓰지 않습니다. 오타가 있는 `TEST CODE REPOSTORY` 같은 섹션 제목은 고칩니다(링크 상자 스타일이 이 제목에 걸려 있습니다).

## 5. 본문 마크업

- 목록 기호는 `-`, 중첩 들여쓰기는 2칸으로 맞춥니다. `*`와 4칸 들여쓰기는 바꿉니다.
- 한 문단을 문장마다 줄바꿈해 둔 경우(빈 줄 없이 이어진 문장들) 한 줄로 이어 붙입니다. 목록, 표, HTML 블록은 제외합니다.
- 블록 아래 간격용 `<br/>`은 지우고, 바로 위 블록(`<div>` 등)에 `class="block-break"`를 붙입니다. 코드 블록과 표 안의 `<br>`은 둡니다.
- 인용문(`>`) 안의 문장은 고치지 않습니다.
- 본문 첫머리나 끝에 남은 `#### RECOMMEND POSTS BEFORE THIS` 같은 추천 글 목록은 frontmatter의 `recommendedPosts`(`title`, `href`)로 옮기고, 더는 쓰이지 않는 링크 정의를 지웁니다. 순서는 글쓴이가 쓴 순서를 따릅니다.

## 6. 이미지

이미지는 `https://raw.githubusercontent.com/Junhyunny/junhyunny-blog-<연도>/main/<파일>` 주소를 쓰고, 아래 형식으로 둡니다. 코드 블록 안의 예시는 제외합니다.

```html
<div align="center">
  <img src="https://raw.githubusercontent.com/Junhyunny/junhyunny-blog-2026/main/example-01.png" width="80%" class="image__border">
</div>
<center>https://출처-주소</center>
```

- `<p align="center">`로 감싼 이미지는 `<div align="center">`로 바꿉니다. `width`, `class`(`image__border`, `image__padding`)는 유지합니다.
- `{{ site.image_url_2022 }}` 같은 Jekyll 변수가 남아 있으면 해당 연도의 저장소 주소로 바꿉니다. Markdown `![]()` 이미지도 위 형식으로 바꿉니다.
- 한 블록에 이미지 두 장 이상을 나란히 둘 때는 `<div class="image-row" align="center">`를 씁니다(각 `img`의 `width`가 그대로 적용됩니다). 위쪽을 맞추려면 `image-row--top`을 더합니다. 같은 크기로 2·3열 격자를 만들 때는 `<div class="image-grid image-grid--2">`(또는 `--3`)를 씁니다.
- 이미지 바로 아래 `<center>`는 출처나 설명입니다. 글쓴이가 쓴 것만 두고 새로 만들지 않습니다.

## 7. TEST CODE REPOSITORY

예제 코드 저장소 링크는 글 끝 `#### TEST CODE REPOSITORY` 아래 목록에 둡니다. 이 소제목 바로 아래 목록은 링크 상자로 보이고, `blog-in-action` 예제 URL은 "저장소 / 예제 이름"으로 자동 표시됩니다.

```markdown
#### TEST CODE REPOSITORY

- <https://github.com/Junhyunny/blog-in-action/tree/master/2026-10-31-kotlin-coroutine-architecture>
```

- 본문 중간에 예제 저장소 URL만 있는 문단이 있고 이 섹션이 없으면 섹션으로 옮깁니다. 문장 안의 링크는 그대로 둡니다.
- 섹션은 `#### REFERENCE`보다 앞에 둡니다.

## 8. REFERENCE

글쓴이가 참고 자료로 밝힌 링크 목록은 글 맨 끝 `#### REFERENCE` 아래에 둡니다. 이 소제목 바로 아래 목록은 하나의 상자로 묶여 보입니다.

```markdown
#### REFERENCE

- <https://kotlinlang.org/docs/coroutines-basics.html>
- [Spring Framework Documentation](https://docs.spring.io/...)
```

- 같은 URL이 여러 번 있으면 하나만 둡니다. 순서는 글쓴이가 쓴 순서를 따릅니다.
- 링크 형식(`<URL>` 또는 `[이름](URL)`)은 글쓴이가 쓴 대로 둡니다. 링크 없이 책 제목만 적은 항목도 그대로 둡니다.
- 목록 바로 위의 `PROMPT(레퍼런스 ...)` 지시문은 이 단계를 수행한 것으로 보고 지웁니다.

## 9. 날짜, 파일 이름, 주소

첨삭을 마친 뒤 처리합니다. 현재 시각은 `TZ=Asia/Seoul date +%Y-%m-%dT%H:%M:%S+09:00`으로 구합니다.

**새 글인지 판단:** `git cat-file -e HEAD:<경로>`가 실패하면 새 글, 성공하면 기존 글입니다. 스테이지만 되고 커밋되지 않은 파일도 새 글입니다. 커밋된 글이 `git status`에서 삭제로 나오고 대상 글과 같은 글로 보이면, 이름만 바뀐 기존 글일 수 있으니 바꾸지 말고 사용자에게 물어봅니다.

| 항목 | 새 글 | 기존 글 |
| --- | --- | --- |
| `updatedAt` | 현재 시각 | 현재 시각 |
| `publishedAt` | 오늘(`YYYY-MM-DD`) | 그대로 |
| 파일 경로 | `src/content/posts/<연도>/<오늘>-<slug>.md` | 그대로 |
| `canonicalPath` | `/<categories를 순서대로 /로 이은 경로>/<slug>/` | 그대로 |

- `updatedAt`은 `YYYY-MM-DDTHH:MM:SS+09:00` 형식으로 씁니다.
- 기존 글의 파일 이름과 `canonicalPath`는 공개된 주소이므로 바꾸지 않습니다. 오타가 있으면 알려 주기만 합니다.
- 새 글의 슬러그는 첨삭한 글 내용을 보고 판단합니다. 오타가 있거나, 내용과 맞지 않거나, 검색될 만한 주제어가 없으면 새로 짓습니다.
  - 글의 핵심 주제어를 담은 영어 소문자 kebab-case 3~6단어로 씁니다. 예: `kotlin-coroutine-architecture`
  - `post`, `new`, `test`, `draft`처럼 뜻이 없는 단어와 날짜는 넣지 않습니다.
  - 빌드는 주소 충돌을 잡아 주지 않으므로 `grep -rn 'canonicalPath: "<새 경로>"' src/content`로 겹치는 글이 없는지 확인하고, 겹치면 다른 이름을 씁니다.
- 이름 변경은 Git이 추적 중인 파일이면 `git mv`, 아니면 `mv`로 합니다. 새 글의 예제 저장소 URL(`blog-in-action/tree/master/<날짜>-<slug>`)이 파일 이름과 달라지면 보고합니다.

## 10. 확인과 보고

1. 코드 블록 밖에 처리하지 않은 `PROMPT(`, `-습니다`, `-입니다`, `-요.`, `-요?`로 끝나는 문장, 1인칭 `저`, `제가`, `{{ site.`, `<p align`, `![`, 간격용 `<br`, `RECOMMEND POSTS`, `*` 목록 기호가 남았는지 검색합니다.
2. 새로 쓰거나 바꾼 이미지 주소마다 `curl -sI`로 확인합니다. 빌드는 없는 이미지를 잡아 주지 않으므로, 200이 아니면 저장소에 파일이 없는 것으로 알려 줍니다.
3. `npm run build`를 실행해 오류와 경고가 없는지 확인합니다.
4. 루트의 `proofread-todo.md`에 이 글이 있으면 `- [ ]`를 `- [x]`로 바꿉니다.
5. 커밋하지 않고, 다음을 짧게 알려 줍니다.
   - 바뀐 내용 요약(오타, 띄어쓰기, 표현, 어체, 소제목 번호, 마크업)과 `PROMPT`를 바꾼 결과
   - `updatedAt` 새 값, 새 글이면 파일 이름과 `canonicalPath`
   - 추가한 소제목, 옮긴 추천 글과 링크, 찾지 못한 이미지
   - 뜻이 바뀌었을 수 있어 글쓴이가 확인할 문장
   - 고치지 않은 문제: `title`이나 기존 글 주소의 오타, 사실이 의심스럽거나 오래된 내용, 남겨 둔 `PROMPT`
